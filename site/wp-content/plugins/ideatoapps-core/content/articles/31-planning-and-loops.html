Here is a made-up trace from a coding agent. Its goal is to reproduce a bug from a user's report. It searches the code for the error message and finds nothing. Then it runs the same search again, and again, until a step limit ends the run with no result and no explanation.

Plan first, or decide each step?

Agent loops usually follow one of two designs. In the first, the model writes the whole plan before it acts, and the loop works through it. A person can review that plan before anything runs, and each step is easy to log. The weak point is surprise, because a plan written before the first tool result is a guess about what the tools will find.

In the second design, the model picks the next action after every tool result. This adapts to whatever it finds. The run is harder to predict, though, and it can move away from the goal as one result leads to another.

Many builders mix the two. The model writes a short plan, works through it, and rewrites the remaining steps when a result doesn't match what the plan expected. In the trace above, that moment came right after the first empty search. Searching with other words, or asking the user for the full error text, would both have moved the task forward.

Keep plans short by putting a step cap in the planning [ita_term define="The message or instructions you type to an AI app to tell it what you want."]prompt[/ita_term]. A person can check every step of a five-step plan before the run starts, which is rarely true of a plan with thirty.

Keep the plan as data

A plan that only exists in the model's earlier replies is hard to inspect. Store it in your code instead, as a list of steps, each with an ID, a description, a status and a short note. A stored plan gives you one place to look, instead of pages of model text.

Send the current plan with each request, and have the model reply with changes in a fixed shape. [ita_term define="A plain-text format for data, made of named fields and values inside curly braces, that most programs can read."]JSON[/ita_term] is a common choice for this. The instructions can then forbid the model from marking a step done without evidence, as in this version:

[ita_prompt title="Plan with status and a stop reason"] Goal: [write a failing test that reproduces bug report 412] Current plan: [the stored plan as JSON, with id, do, status and note for each step] Last tool result: [the last tool result] Reply with one JSON object and nothing else, in this shape: {"update": [{"id": 2, "status": "done", "note": "test file created"}], "add": [], "next_action": "run_tests", "stop": "NONE"} Allowed status values: todo, doing, done, failed, skipped. Allowed stop values: NONE, GOAL_MET, BLOCKED. If BLOCKED, add a "question" field for the user. Mark a step done only if the last tool result shows it. If a step failed, rewrite the steps after it before you choose the next action. [/ita_prompt]

Your code applies each update and rejects any that break the rules. A step moves to done only when a matching tool result is in the log. An unknown step ID is an error, and so is a jump from todo to done with no tool call in between. All of this comes after the usual check that the reply is valid JSON. Budget, no-progress and canceled stops come from your code, so the model never needs to report them.

A stored plan also helps after a crash or a timeout: the loop can restart from the first unfinished step. First check whether a step left in "doing" already changed something, so a restart doesn't repeat it.

Stop conditions the model can't change

An instruction like "stop when you're done" is a request to the model, and the model may decide too early, too late or never. The limits that matter belong in the loop's code, and every run should end with a stop reason your logs can count.

The good ending is that the goal is met. Check that in code where you can. In the bug example, the new test should fail with the error from the report. A second ending is a spent budget. Cap steps, time and [ita_term define="Small pieces of text, often parts of words, that a model reads and writes."]tokens[/ita_term] per run, and set each cap a little above what normal runs use.

The third ending is no progress. The same call keeps returning the same result, or the plan hasn't changed in several steps. The fourth is blocked, when the model needs information or an approval it can't get, so it returns one clear question to the user. The last is the simplest: a person canceled the run.

A run that ends with "blocked: need the full error text" gives the user something to do. A run that only ever ends at the step cap is probably missing a no-progress check. The last few log lines usually show where the repeating started.

[ita_why title="How a loop can notice it's stuck"]

A common no-progress check compares recent steps. For each call, your code can store two things: the tool name with its arguments, and a [ita_term define="A short code computed from a piece of text; the same text always gives the same code."]hash[/ita_term] of the result. If the same pair appears again, the model is repeating itself. Hash only the meaningful part of a result, since timestamps or request IDs make identical results look different.

Also count failures per step and count plan rewrites. A step that has failed several times, or a plan rewritten again and again with no step reaching done, is a good point to stop and report.

Some repeats are correct, for example when the agent checks on a slow job. Those tools need their own rule: a fixed wait between checks and a maximum number of checks.

Try it

This takes a short work session with a test copy of your agent.

  1. Check that a step or time cap is set, so the run can't go on forever. Then add a tool that always returns the same error.
  2. Give the agent a goal that needs that tool, and run it.
  3. Read the log and count how many identical calls happen before anything ends the run.
  4. Add a no-progress check that compares tool name, arguments and result hash, plus a stop reason, then run it again and confirm the log ends with "no progress".
