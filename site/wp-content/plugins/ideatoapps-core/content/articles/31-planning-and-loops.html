Here is a made-up trace from a coding agent. Its goal is to reproduce a bug from a user's report. It searches the code for the error message and finds nothing. Then it runs the same search again, and again, until a step limit ends the run with no result and no explanation. If you've built an agent, you've probably watched a run like this one.

Plan first, or decide each step?

Agent loops usually follow one of two designs. In the first, the model writes the whole plan before it acts, and the loop works through it. A person can review that plan before anything runs, and each step is easy to log. The weak point is surprise, because a plan written before the first tool result is a guess about what the tools will find.

In the second design, the model picks the next action after every tool result. This adapts to whatever it finds. The run is harder to predict, though, and it can wander away from the goal as one result leads to another.

Many builders mix the two. The model writes a short plan, works through it, and rewrites the remaining steps when a result doesn't match what the plan expected. In the trace above, that moment came right after the first empty search. Searching with other words, or asking the user for the full error text, would both have moved the task forward.

Keep plans short by putting a step cap in the planning [ita_term define="The message or instructions you type to an AI app to tell it what you want."]prompt[/ita_term]. A person can check every step of a five-step plan before the run starts, which is rarely true of a plan with thirty.

Keep the plan as data

A plan that only exists in the model's earlier replies is hard to inspect. Store it in your code instead, as a list of steps, each with an ID, a description, a status and a short note. If you've ever debugged a run by scrolling through pages of model text, you'll like having one place to look.

Send the current plan with each request, and have the model reply with changes in a fixed shape. Most builders use [ita_term define="A common text format for structured data, written as named fields and values inside curly braces."]JSON[/ita_term] for this. The instructions can then forbid the model from marking a step done without evidence. Here is one version (example values: replace them):

[ita_prompt title="Plan with status and a stop reason"] Goal: [write a failing test that reproduces bug report 412] Current plan: [the stored plan as JSON, with id, do, status and note for each step] Last tool result: [the last tool result] Reply with one JSON object and nothing else, in this shape: {"update": [{"id": 2, "status": "done", "note": "test file created"}], "add": [], "next_action": "run_tests", "stop": "NONE"} Allowed status values: todo, doing, done, failed, skipped. Allowed stop values: NONE, GOAL_MET, BLOCKED. If BLOCKED, add a "question" field for the user. Mark a step done only if the last tool result shows it. If a step failed, rewrite the steps after it before you choose the next action. [/ita_prompt]

Your code applies each update and rejects any that break the rules. A step moves to done only when a matching tool result is in the log. An unknown step ID is an error, and so is a jump from todo to done with no tool call in between. All of this comes after the usual check that the reply parses as JSON at all.

A stored plan also helps after a crash or a timeout, because the loop can restart from the first unfinished step.

Stop conditions the model can't change

An instruction like "stop when you're done" is a request to the model, and the model may decide too early, too late or never. The limits that matter belong in the loop's code, and every run should end with a stop reason your logs can count.

The good ending is that the goal is met. Check that in code where you can. In the bug example, the new test should fail with the error from the report. A second ending is a used-up budget: cap steps, time and [ita_term define="Small pieces of text, often parts of words, that a model reads and writes."]tokens[/ita_term] per run, and set the caps from runs you've watched, with some room to spare.

The third ending is no progress. The same call keeps returning the same result, or the plan hasn't changed in several steps. The fourth is blocked, when the model needs information or an approval it can't get, so it returns one clear question to the user. The last is the simplest: a person canceled the run.

A run that ends with "blocked: need the full error text" gives the user something to do. A run that hits the step cap with no reason is a bug in the loop, and the last few steps of its log usually show where the repeating started.

[ita_why title="How a loop can notice it's stuck"]

Most no-progress checks compare recent steps. Your code can keep a short history of each call as a pair: the tool name with its arguments, and a fingerprint of the result, such as a [ita_term define="A short code computed from a piece of text; the same text always gives the same code."]hash[/ita_term] of the returned text. If the same pair appears again, the model is repeating itself.

Also count failures per step and count plan rewrites. A step that has failed several times, or a plan rewritten again and again with no step reaching done, is a good point to stop and report.

Some repeats are correct, for example when the agent checks on a slow job. Those tools need their own rule: a fixed wait between checks and a maximum number of checks.

  2. Give the agent a goal that needs that tool, and run it.
  3. Read the log and count how many identical calls happen before anything ends the run.
