When an agent does something wrong, the first urge is often to run the task again. A second run might work. It might also repeat the mistake and add a new one, leaving two sets of changes to undo. If you've ever had to explain to a customer why they got two messages that disagree, you know how quickly that gets worse.

What it looks like

You've probably met a version of this before agents existed: an automatic email that went to the wrong list. Agent failures are similar, and most causes come from one of three things: the goal and [ita_term define="The message or instructions you type to an AI app to tell it what you want."]prompt[/ita_term] it was given, the tools it had, or the text it read.

Say a delivery company's dispatch office uses an agent to move delivery slots and text customers the new time. Each row of this table could happen there.

The hidden-instruction row is the hardest one. It has no complete fix yet, which is why "What is an AI agent" stresses limited tools and approvals.

The first hour

In the first minutes

Pause the agent, including any scheduled runs. If you can't pause it, turn off the tool it used, such as its access to the text service. Every minute it keeps running can add another change to undo.

Within the hour

List what changed: messages sent, bookings moved, files edited. The tool log is the most reliable record. Undo what you can, such as moving the delivery slot back. For messages already sent, follow your workplace's usual process for telling customers about a mistake.

Before anyone runs it again

Save the log, the inputs and the instructions as they were at the time. Then name the cause, using the table above.

A long log is hard to read under pressure, and a chatbot can turn it into a short summary. Remove customer names and phone numbers first, and paste a work log only if your workplace allows it. Check the summary against the log before you share it.

Fixing the cause

Each cause has a typical fix:

  • Unclear goal: narrow it, and say what "done" means.
  • Too many tools: remove the ones the task doesn't need, or make them read-only.
  • A risky action ran without anyone seeing it: add an approval step before that action.
  • Old or wrong inputs: add dates and sources to what it reads, and remove stale notes.
  • Outside text gave instructions: limit what the agent may do after reading untrusted text, such as no sending without approval.
  • The same wrong judgment again and again: break the task into fixed steps, so the model makes fewer choices.

A builder can also add the failed case to the agent's test set. Rerun it in a safe setup before real work starts again, and write the cause and the fix where your team can find them.

[ita_why title="How an agent can report success that didn't happen"]

The model writes the text that is most likely to come next. After a step like "text the customer", the likely next words include "Done, the customer has been told." That can happen even when the tool call failed, or was never made.

Well-built agent programs record each tool call and its status separately from the model's own words. When the summary and the tool log disagree, the log is the one that shows what ran.

Try it

Do this as a short talk with a coworker who uses the same agent or automation. Nothing gets run.

  1. Pick one agent or automated task your team uses, or one you plan to use.
  2. Each of you writes down one way it could go wrong, using a row of the table above.
  3. For each, answer two questions: how would we notice, and who would notice first?
  4. Write what would need undoing, and whether anyone outside the team would need to be told.
  5. Agree who can pause the agent, and write down where the pause setting is.
