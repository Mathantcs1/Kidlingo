If you build an app on top of a language model, two parts of each [ita_term define="The message or instructions you type to an AI app to tell it what you want."]prompt[/ita_term] your app sends do most of the steering. The [ita_term define="The standing instructions an app sends to the model before the user's messages, setting its scope, rules and output format."]system prompt[/ita_term] sets the rules for every conversation. A structured-output request makes each reply far more likely to be something your code can parse. Neither one is a security boundary, so design for that from the start.

What goes in a system prompt

A system prompt is plain text the model reads before anything the user writes. Keep it organized, so you and your teammates can find and change one rule without breaking another. A useful order is scope, facts, rules, then the output contract.

Here is a skeleton for a hypothetical booking assistant at a pet-grooming shop. The app adds the free time slots to each request, so the model never invents them:

[ita_prompt title="System prompt skeleton"] ## Scope You help customers of [shop name], a pet-grooming shop, book, move or cancel appointments. You do not give health advice about animals. For health questions, suggest contacting a vet. ## Facts Opening hours: [hours] Services and how long each takes: [list] Free slots: only the times listed in the FREE_SLOTS block that the app adds to each message. ## Rules - Ask for the pet's size and the service before offering times. - Offer only times from FREE_SLOTS. - Never say a booking is confirmed. Return a booking request; the app confirms it. ## Output Reply with one JSON object and nothing else, in this shape (the values are examples): {"reply": "text shown to the customer", "action": "show_times", "booking": null} "action" must be one of: "none", "show_times", "request_booking". "booking" is null, or {"service": "...", "pet_size": "small", "start": "YYYY-MM-DDTHH:MM"}, where "pet_size" is one of "small", "medium", "large" and "start" is in the shop's local time. If you cannot help, set "action" to "none", set "booking" to null and explain in "reply". [/ita_prompt]

Every output contract needs a defined way to say "I can't do this". Without one, the model is likely to invent a value to fill the shape. A clear fallback lets your code handle a refusal like any other branch.

Getting output your code can parse

  1. Show the shape. An example object or a short schema beats a paragraph describing fields. Use fixed lists of allowed values (enums) wherever you can.
  2. Use the API's structured mode if it has one. Some providers can constrain replies to valid JSON or to a schema you send. The options differ between providers and change over time, so check the current documentation for yours.
  3. Validate anyway. Valid JSON can still hold a slot that isn't free or a date in the past. Check values against your own data in code.
  4. Plan the failure path. On a parse or validation error, retry once with the error message included. This includes replies cut off at the output token limit, which can happen even in a structured mode. If that fails too, send a safe reply such as "Sorry, please call the shop."
  5. Keep the schema small. Fewer, flatter fields are easier for the model to fill correctly and easier for you to test.

Field order can matter, because the model writes the object from top to bottom. Some builders put a short "reason" field before a "decision" field for that reason. Whether it helps depends on the model and the task, so test it on your own cases.

Questions builders often ask

Can a user override the system prompt?

Sometimes, yes. Text in a user message, an uploaded document or a tool result can contain instructions, and the model may follow them. This is called [ita_term define="Text written to make a model ignore its instructions and follow new ones, hidden in user input, documents or web pages."]prompt injection[/ita_term], and there is no complete fix yet. Treat the system prompt as strong guidance, and enforce anything that matters in code. Here, the app checks the slot and the customer before it books.

Can I keep secrets in it?

No. Assume a determined user can get the model to repeat the system prompt. API keys, internal prices and private data belong in your server code, never in the text the model sees.

How long should it be?

As long as the rules need and no longer. Every token in it is sent with every request, and rules that contradict each other are harder to spot in a long prompt. When you add a rule, check whether it replaces an old one.

How do I know a change helped?

Keep a small set of test messages and rerun them after every edit. A change that fixes one case can break another, and you'll only see that if you run the same set each time.

[ita_why title="Where does the system prompt actually go?"]

In chat-style APIs, a request is usually a list of messages, each with a role: system, user or assistant. Before the model reads them, the list is turned into one sequence of tokens with special markers between the roles.

Models are usually trained to give the system part extra weight. That weight comes from training, though, not from a hard rule in the software. So a system prompt works well most of the time, and a cleverly written user message can still lead the model away from it.

Try it

Write a test sheet that a teammate could run without you.

  1. Write five user messages for your app or the grooming example. Include two normal requests, one out of scope, one vague, and one that says to ignore the rules.
  2. Next to each, write the expected action value and one sentence on what a good reply does.
  3. Run all five against your current system prompt and save the raw output.
  4. Mark each one pass or fail, and note any reply your parser or validator rejected.
  5. Commit the sheet next to the system prompt in your repository, so every future edit is tested against it.
