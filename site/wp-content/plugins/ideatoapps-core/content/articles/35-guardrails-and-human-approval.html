Guardrails are the limits around an agent: what it may read, which tools it may use, and how far it may go. Human approval is one guardrail among several. Before certain actions, the agent stops and a person says yes or no.

Where the rules live

A [ita_term define="A rule around an AI system that limits what it can do, checked before or after the model acts."]guardrail[/ita_term] can live in two places. It can be an instruction in the agent's [ita_term define="The message or instructions you type to an AI app to tell it what you want."]prompt[/ita_term], such as "never message anyone outside the volunteer list". Or it can be a check in the program that runs the agent's tools.

Instructions are useful, but the model can misread them, lose track of them in a long run, or be misled by text it reads. A check in code runs every time. Put the rules that must hold in code, and use instructions to explain them to the model.

Imagine a community food bank that uses an agent to help its volunteer coordinator. The agent drafts shift reminders, updates the sign-up sheet and orders supplies. Guardrails in code could include these:

  • Messages go only to addresses on the volunteer list.
  • Orders use only items from the approved supply list, with a cap on quantity per order.
  • The agent has no tool for changing bank details or deleting the volunteer list.
  • Outgoing text is checked for phone numbers and home addresses before it leaves.
  • Each run has a step limit and a log.

What needs a person

[ita_figure name="guardrail-approval-flow" alt="An agent proposes an action. A risk check lets low-risk actions run; risky ones wait for a person, who approves them or stops them." caption="Rules set the limits; a person decides on the risky actions."]

If you've ever clicked "Allow" on a pop-up without reading it, you already know the problem with asking about everything. People who approve dozens of requests a day start to click yes without reading. Sort the agent's actions into four groups instead:

  • Run: reading, searching and drafting. Nothing leaves the system.
  • Run and report: small changes that are easy to undo, such as moving a volunteer between two shifts they signed up for. They appear in a daily list someone reads.
  • Ask first: anything sent to people, anything that spends money, and anything that changes a shared record in a way that's hard to undo.
  • Never: actions the agent has no tool for at all.

To decide where an action goes, ask: Who sees the result? Can it be undone, and by whom? Does it spend money or make a promise? What happens if it's wrong once a day for a month? If any answer worries you, the action goes in "ask first".

Approval requests people read

An approval is only as good as the request behind it. "Send reminders? Yes or no" gives the coordinator nothing to check. You've probably seen the other extreme too: a request so long that nobody reads past the first line. A good request shows the exact action, the exact content, who is affected and whether it can be undone.

If you build or configure the agent, you can require that format in its instructions. Put your own list of actions in the brackets (example values: replace them):

[ita_prompt title="Approval request format"] Before any of these actions, stop and ask for approval: [sending a message to more than one person; ordering supplies; changing the shift sheet] Write each approval request in exactly this form: Action: ONE LINE Exact content: THE FULL MESSAGE OR CHANGE, WORD FOR WORD Who is affected: GROUP NAME AND NUMBER OF PEOPLE Can it be undone: YES, AND HOW, or NO Reason: ONE LINE Then wait. If the reply is anything other than "approve", do not take the action. [/ita_prompt]

Back this up in code. The program should run only the exact action that was approved, and treat no answer as no. If the model changes the message after approval, it needs a new approval.

The approval log is worth a look every few weeks. Actions that are always approved without changes may belong in "run and report", and actions that are often declined point to a problem in the agent's goal or inputs.

[ita_why title="What approval can't catch"]

An approver can only judge what the request shows. A request can look fine while the problem sits somewhere else: a wrong goal, an old volunteer list, or an approved action that triggers another one later.

Long or technical requests are also easy to approve without understanding them. So approval works best together with the other guardrails: narrow tools, checked inputs and limits in code.

Try it

Use any agent or automation you use or plan, at work or as a volunteer.

  1. List every action it can take, one per line. Include reading and drafting.
  2. Sort the actions into four groups: run, run and report, ask first, never.
  3. For each "ask first" action, write the details the approval request must show.
  4. For each "never" action, check whether the agent still has a tool that could do it, and if it does, ask whoever configured the agent to remove that tool.
