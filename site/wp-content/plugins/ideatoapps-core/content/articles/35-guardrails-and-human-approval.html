Guardrails are the limits around an agent: what it may read, which tools it may use, and how far it may go. Human approval is one guardrail among several. Before certain actions, the agent stops and a person says yes or no.

Where the rules live

A [ita_term define="A rule around an AI system that limits what it can do, checked before or after the model acts."]guardrail[/ita_term] can live in two places. It can be an instruction in the agent's [ita_term define="The message or instructions you type to an AI app to tell it what you want."]prompt[/ita_term], such as "never message anyone outside the volunteer list". Or it can be a check in the program that runs the agent's tools.

Instructions are useful, but the model can misread them, forget them in a long run, or be misled by text it reads. A check in code runs every time. Put the rules that must hold in code, and use instructions to explain them to the model.

A community food bank shows how this works. Its volunteer coordinator uses an agent that drafts shift reminders, updates the sign-up sheet and orders supplies. Guardrails in code could include these:

  • Messages go only to addresses on the volunteer list.
  • Orders use only items from the approved supply list, with a cap on quantity per order.
  • The agent has no tool for changing payment details or deleting the volunteer list.
  • Outgoing text is checked for volunteers' phone numbers and home addresses before it leaves. Such checks catch many cases, not all.
  • Each run has a step limit and a log.

What needs a person

[ita_figure name="guardrail-approval-flow" alt="An agent proposes an action. A risk check lets low-risk actions run; risky ones wait for a person, who approves them or stops them." caption="Rules set the limits; a person decides on the risky actions. Actions in the never group have no tool at all."]

If you've ever clicked "Allow" on a pop-up without reading it, that was approval fatigue in a small form. People who approve dozens of requests a day often start to click yes without reading. Sort the agent's actions into four groups instead:

  • Run: reading, searching and drafting. Nothing leaves the system.
  • Run and report: small changes that are easy to undo, such as moving a volunteer to another shift they already said they could do. They appear in a daily list someone reads.
  • Ask first: anything sent to people, anything that spends money, and anything that changes a shared record in a way that's hard to undo.
  • Never: actions the agent has no tool for at all.

To decide where an action goes, ask: Who sees the result? Can it be undone, and by whom? Does it spend money or make a promise? What happens if it's wrong once a day for a month? If any answer worries you, the action goes in "ask first".

[ita_why title="What approval can't catch"]

An approver can only judge what the request shows. A request can look fine while the problem is somewhere else: a wrong goal, an old volunteer list, or an approved action that triggers another one later.

Long or technical requests are also easy to approve without understanding them. This is why the food bank's agent also has a capped supply list and no tool for deleting volunteers.

[/ita_why]

Approval requests people read

"Send reminders? Yes or no" gives the coordinator nothing to check. A request so long that nobody reads past the first line fails too. A good request shows the exact action, the exact content, who is affected and whether it can be undone.

If you build or configure the agent, you can require that format in its instructions. Put your own list of actions in the brackets:

[ita_prompt title="Approval request format"] Before any of these actions, stop and ask for approval: [sending a message to more than one person; ordering supplies; changing the shift sheet] Write each approval request as five labeled lines: Action: the action in one line Exact content: the full message or change, word for word Who is affected: the group and the number of people Can it be undone: yes and how, or no Reason: one line Then wait. If the reply is anything other than APPROVE, do not take the action. [/ita_prompt]

The program has to enforce the same rules. Have it fill in the action and the exact content from the real tool call, so the request can't differ from what will run. It should run only the exact action that was approved, and treat no answer as no. If the model changes the message after approval, it needs a new approval.

Read the approval log every few weeks. Actions that are always approved without changes may belong in "run and report", and actions that are often declined point to a problem in the agent's goal or inputs.

Try it

Pick an agent or automation you use, or plan to use, at work or as a volunteer.

  1. List every action it can take, one per line. Include reading and drafting.
  2. Sort the actions into four groups: run, run and report, ask first, never.
  3. For each "ask first" action, write the details the approval request must show.
  4. For each "never" action, check whether the agent still has a tool that could do it, and if it does, ask whoever configured the agent to remove that tool.
