Can you run a language model on your own laptop or desktop? In many cases, yes. Smaller [ita_term define="A model whose trained numbers (its weights) are published, so anyone can download and run it."]open-weight[/ita_term] models can run on ordinary computers, and faster with a recent graphics card or plenty of memory. You usually give up some speed and capability for privacy and control.

Setting it up

What do I need?

Two things: the model files and a program that runs them. The files hold the model's [ita_term define="The trained numbers inside a model, also called its parameters."]weights[/ita_term], and you need a model whose license allows your use (see "Open vs closed models"). Many models come in several sizes, and a small one is the easier first test.

The program, called a runner, loads the files and lets you chat with the model or call it from code. Many runners can also start a local server that accepts requests in a format similar to common hosted [ita_term define="Application programming interface: the connection a program uses to send requests to a model and get answers back."]APIs[/ita_term]. That means your code can switch between local and hosted with small changes. Keep that server reachable only from your own machine unless you add access controls, because anyone who can reach it can use your model.

Will it fit on my machine?

For good speed, the whole model usually needs to fit in the graphics card's memory, or in fast main memory on some machines. If it doesn't fit, the runner may split the work or refuse to load, and speed can drop sharply. If you've ever watched a model type one word every few seconds, this is the usual cause.

Is it safe to download models?

Treat model files like any other software. Download them only from sources you trust. Some file formats can run code when they're loaded, so prefer formats that store only the numbers. Keep your runner updated, and keep turned off any option that runs code included with a model unless you trust where it came from.

[ita_why title="How a big model fits into less memory"]

A model's weights are numbers, and each number takes a certain number of bits to store. [ita_term define="Storing a model's numbers with fewer bits each, so it needs less memory."]Quantization[/ita_term] rounds them so each one uses fewer bits.

The file gets smaller, the model needs less memory, and it can run faster. The cost is some loss of quality, which grows as fewer bits are used. Many local model files are offered at several quantization levels, so it's worth trying more than one on your own tasks.

[/ita_why]

Living with a local model

How fast and how good will it be?

You'll probably notice the speed first. Replies can arrive more slowly than from a hosted service, and the first request can take longer while the model loads. Smaller models make more mistakes on hard reasoning, long documents and complex instructions. They can be fine for focused jobs like extracting fields, sorting short messages or rewording text. General reviews go out of date quickly, so the only judgment that counts is a test on your own tasks.

How much text can I send?

Memory use grows with the length of the input. On your machine, the usable [ita_term define="The amount of text, counted in tokens, that a model can take into account at one time."]context window[/ita_term] can be smaller than the model's stated maximum. Some runners also start with a small default context length, which is a setting worth checking before you blame the model for forgetting.

What's missing compared with a hosted app?

Hosted apps add features around the model, such as web search, file reading and safety filters. Locally, you get what's in the weights, what your runner adds and what you build yourself. Your machine also does all the work, so expect heat, fan noise and battery drain during long runs.

Does my text stay private?

Privacy is a common reason builders run models locally. Your text stays on your machine as long as the runner doesn't send anything out. Its settings for update checks, usage reports and optional online features tell you whether it does.

Prompting a smaller model

Smaller models follow long, layered instructions less reliably. A [ita_term define="The message or instructions you type to an AI app to tell it what you want."]prompt[/ita_term] works better when it gives one job, marks where the input starts and ends, and shows the exact output shape. Keep the input short enough to leave room for the reply. If a task needs several steps, send each step as its own request and join the results in your code. Here is a single-job prompt for pulling dates out of a note:

[ita_prompt title="One task, marked input"] You extract dates. Do one task only. Task: list every date in the text below and what happens on that date. Output: one line per date, in this form: YYYY-MM-DD | event If a date has no year or is relative, such as next Tuesday, copy it as written and add (unclear). If the text has no dates, output only: NONE ### TEXT START [paste the text] ### TEXT END [/ita_prompt] [ita_quiz] [ita_q q="A local model loads, but replies are extremely slow. Try it

A quick version, before you download anything:

  1. Write five short test tasks from your real work, for example pulling dates from a note or summarizing a page of documentation. Remove names, and use real text only if your workplace allows it.
  2. Run the five tasks on the hosted model you use now, and mark which answers you would accept.
  3. After you install a local model, run the same five tasks and mark each answer "good enough" or "not good enough".
