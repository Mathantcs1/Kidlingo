Function calling lets a language model ask your code to do something: find data, run a calculation, add an event to a calendar. You describe the tools your app offers. The model replies either with text or with a structured request that names a tool and its inputs. Your code runs the tool and returns the result.

Most of the engineering work is in two places: the tool descriptions, and what your code does with each request.

One round trip

[ita_figure name="tool-calling" alt="You ask a question, the model sends a request to a tool, the tool sends a result back, and the model writes the answer." caption="The model asks for a tool; your code runs it and returns the result."]
  1. Your app sends the request. It includes the conversation and a list of tool definitions: a name, a description and an input [ita_term define="A description of the shape data must have: its fields, their types and allowed values."]schema[/ita_term].
  2. The model chooses. It writes a normal answer, or it returns a tool call: a tool name plus [ita_term define="The input values passed to a function, such as a date or a title."]arguments[/ita_term] in a structured format, usually JSON.
  3. Your code runs it. It checks the arguments, calls the real function and captures the result or the error.
  4. Your code returns the result. The result is labeled as the answer to that call, usually with an ID that links the two.
  5. The model continues. It writes the final answer or asks for another tool.

Some APIs let the model ask for several calls in one turn. Some let your code force a tool call, or force one particular tool. Field names and formats differ between providers and change over time, so check the current documentation for yours.

Writing a tool definition

The model chooses tools from their names and descriptions. Write the description as you would write a [ita_term define="The message or instructions you type to an AI app to tell it what you want."]prompt[/ita_term]: say when to use the tool, and when not to. Here is a definition for a hypothetical family calendar app:

[ita_prompt title="A tool definition"] (example values: replace them) { "name": "add_family_event", "description": "Add one event to the shared family calendar. Use only after the user has confirmed the title, date and start time. Do not use for reminders or to-do items.", "parameters": { "type": "object", "properties": { "title": {"type": "string", "description": "Short event title, for example: Dentist checkup"}, "start": {"type": "string", "description": "Local start time as YYYY-MM-DDTHH:MM"}, "duration_minutes": {"type": "integer", "minimum": 5, "maximum": 720}, "who": {"type": "array", "items": {"type": "string", "enum": ["parent_1", "parent_2", "child_1", "child_2"]}} }, "required": ["title", "start"] } } [/ita_prompt]

Wrap it in the format your provider expects. A few habits help the model choose well:

  • Use fixed lists of values wherever you can, like the who field above.
  • Offer few tools, with clear differences. Several tools with similar names and descriptions make wrong choices more likely.
  • Return short results. Return only the fields the model needs.
  • Return errors the model can act on. "Start time is in the past; ask the user for a new time" lets it recover. A stack trace doesn't.
[ita_why title="What the model actually sees of a tool"]

The model doesn't receive your function. Your tool definitions are turned into text and added to the request, usually near the system instructions. The model learned in training to read that text and to write calls in the expected format.

So the definitions use space in the context window on every request, and every description works as part of your instructions. A vague description changes behavior just as a vague instruction would.

[/ita_why]

Checks your code must make

A tool call is a request from the model. Your code decides whether to run it. Validate the arguments as you would any structured output (see "System prompts and structured output for builders"). Then add checks that only matter for tools:

  • Permissions. Check that this user may do this action on this data. Never rely on the model to enforce access.
  • Confirmation. For actions that are hard to undo, such as sending, paying or deleting, show the user the exact action and wait for approval.
  • Repeated calls. A model can repeat a call, and your app can retry after a timeout. Make sure the same event isn't added twice.
  • Tool results as data. A web page or an email returned by a tool can contain text that looks like instructions. Never let a tool result trigger a new action by itself.
  • Limits. Cap the number of calls per request and log each call with its arguments and result.

Try it

  1. Pick one function your app already has, and write a tool definition for it, with a "Use only when" and a "Do not use for" line.
  2. Write three user messages that should call it, and two that look similar but shouldn't.
  3. Send all five with the definition, and log whether a call was made and with which arguments.
  4. Mark each result: right tool, wrong tool, or wrong arguments.
  5. Rewrite the description for every message that went the wrong way, then send all five again.
