[ita_term define="Model Context Protocol: an open standard for how AI apps find and use tools and data offered by separate programs called servers."]MCP[/ita_term] is an open standard for connecting AI apps to tools and data. A developer writes one connector, called a server, and any app that supports the standard can use it. If you've ever written the same integration twice for two different AI apps, that duplicate work is the problem it addresses. Before shared standards like this, each app usually needed its own custom integration for each service.

A connector also gives a model new ways to act on your accounts, so treat installing one like installing software.

Common questions

What are hosts, clients and servers?

The host is the app the user works in: a chat app, a code editor or your own agent. Inside the host, a client keeps a connection to one server. The server is a separate program that offers capabilities, and a host can connect to several servers at once.

What does a server offer?

Usually tools the model can call. Many servers also offer resources, which are data the host can read, such as files or records, and reusable [ita_term define="The message or instructions you type to an AI app to tell it what you want."]prompt[/ita_term] templates. Not every server offers all three.

How does the model see these tools?

When a client connects, it asks the server what it offers. The server returns tool definitions with a name, a description and an input [ita_term define="A description of the shape data must have: its fields, their types and allowed values."]schema[/ita_term]. The host adds them to the model's request, and from there it's the same round trip covered in "Tools and function calling". The model still reads definitions and writes tool calls. The standard changes how the host finds the tools and passes the calls on.

Where does a server run?

A local server runs on the user's machine, usually started by the host. A remote server runs somewhere else and is reached over the network, often after the user signs in to the service behind it. Details such as how hosts connect and how sign-in works have changed between versions of the specification, so the version a host supports decides what your server must handle.

Writing a server

If you're exposing your own service, the habits from writing tool definitions still apply, with a few additions:

  • Few tools with clear differences. Hosts often load tools from several servers at once, so vague or overlapping names cause more wrong choices than they would in a single app.
  • Read-only tools first. Ship search and read actions before anything that writes, sends or deletes.
  • Narrow access. Ask for the smallest [ita_term define="Named permissions that limit what a sign-in can do, such as read-only access to one folder."]scopes[/ita_term] the tools need, and check the user's permissions on every call in your server.
  • Stable names. Hosts and users may approve tools by name, so renaming a tool or changing what it does should be a visible change.

Keep results short and errors clear, as with any tool. Every result uses space in the model's [ita_term define="The amount of text a model can take into account at one time."]context window[/ita_term], and a server's results share that space with every other server the host has loaded.

Before you connect a server

You've probably installed a browser extension without reading what it could access. A server deserves more care than that, because a model will act through it. Check these points before connecting one to real data:

  • Who wrote it. A local server is a program running on your machine. Install only from sources you trust, use a fixed version, and read the code or at least the full tool list.
  • What the descriptions say. Tool descriptions are text the model reads, so a careless or hostile server can hide instructions there, and its results can carry them too.
  • What the tools add up to. An agent that reads untrusted text, can see private data and can also send messages out can be steered into leaking that data. Avoid giving one agent all three.
  • What changes later. A server can change its tools after you reviewed it, so review it again after updates.

[ita_why title="Local and remote servers carry different risks"]

A local server usually runs as a process with the permissions of the user account that starts it. If its code can read files or run commands, a bug or a hostile update can reach anything that account can reach. Running it in a [ita_term define="A sealed-off area on a computer that limits which files and programs a program inside it can reach."]container[/ita_term] or under a limited account reduces that.

A remote server holds [ita_term define="Secret strings that let a program act on your account, usually with limited permissions."]access tokens[/ita_term] to your accounts on someone else's machine. The question changes from "what code runs here?" to "who holds my tokens, with which scopes, and can I revoke them?" Separate, narrow tokens per server limit the damage, and tokens you no longer use should be revoked.

Try it

  2. Next to each, write what it can read and what it can change or send.
  3. Rank them by the harm a wrong or tricked call could cause, worst first.
  4. For the top one, remove a write tool or a scope it doesn't need, or turn on approval for its write tools, then run one normal task to confirm it still works.
